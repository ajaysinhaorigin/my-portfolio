## What Is Observer?

The Observer pattern defines a **one-to-many relationship** between objects.

When the **subject** (the thing being watched) changes, all its **observers** (the watchers) are automatically notified and updated.

Think of it as a subscription system:

- The subject maintains a list of observers
- Observers subscribe to the subject
- When the subject changes, it notifies all subscribers

<Callout type="definition">
  **Observer** = When one thing changes, multiple things automatically react.
</Callout>

---

## Why Does This Pattern Exist?

Imagine you are building a stock trading app. You have:

- A price ticker that shows the current stock price
- A chart that visualizes price history
- An alert system that notifies when price crosses a threshold
- A portfolio display that shows total value

All of these need to update when the stock price changes.

**Without Observer:**

```js
function updateStockPrice(stock, newPrice) {
  stock.price = newPrice;
  
  // Manually update everything
  priceTickerDisplay.update(stock);
  chartDisplay.update(stock);
  alertSystem.check(stock);
  portfolioDisplay.recalculate();
}
```

**Problems:**

- The update function knows about every display component.
- Adding a new display means editing this function.
- Tight coupling — everything is connected.
- Hard to test — you need all components present.

**With Observer:**

```js
// Stock is the subject
stock.setPrice(newPrice); // Just update the price

// All observers are automatically notified
// No need to manually call each one
```

Every observer is automatically notified without the subject knowing who they are.

## The Problem

```js
class User {
  constructor(name) {
    this.name = name;
    this.email = "";
  }

  updateEmail(newEmail) {
    this.email = newEmail;
    
    // Manually trigger everything
    emailVerificationService.sendVerification(this);
    analyticsService.trackEvent("email_updated", this);
    auditLog.log(`User ${this.name} updated email`);
  }
}
```

**Problems:**

1. **Tight coupling** — User class knows about every service.
2. **Not extensible** — adding a new listener means editing User.
3. **Violates SRP** — User has too many responsibilities.
4. **Hard to test** — must mock all services.

---

## What Is Wrong With This Approach?

- Every new feature that reacts to email change requires modifying the `updateEmail` method.
- The User class is coupled to every service.
- Cannot add observers at runtime.
- Difficult to maintain as the system grows.

---

## The Idea Behind the Pattern

What if the User class did not know about the services?

Instead:

1. Services **subscribe** to the User.
2. When User changes, it **notifies** all subscribers.
3. User does not know who the subscribers are — it just notifies them.

This decouples the subject from the observers.

---

## How Does It Work?

### Step-by-Step

1. **Subject** maintains a list of observers.
2. Observers **subscribe** to the subject.
3. When the subject's state changes, it **notifies** all observers.
4. Each observer updates itself based on the notification.

## Structure

```text
         Subject
    ┌──────────────┐
    │  Subject     │
    ├──────────────┤
    │ + attach()   │ ← observers subscribe
    │ + detach()   │ ← observers unsubscribe
    │ + notify()   │ ← tells all observers
    └──────────────┘
            │
            │ maintains list
            ▼
    ┌──────────────┐
    │  Observer    │ (interface)
    ├──────────────┤
    │ + update()   │
    └──────────────┘
            △
            │ implements
    ┌───────┴────────┐
    │                │
┌────────┐      ┌────────┐
│ObserverA│      │ObserverB│
├────────┤      ├────────┤
│update()│      │update()│
└────────┘      └────────┘
```

**Key parts:**

- **Subject** — the object being watched
- **Observer** — the interface all observers implement
- **Concrete Observers** — classes that react to changes

## Simple Real-World Analogy

Think of a **YouTube channel**.

- **Subject:** The channel (YouTuber)
- **Observers:** Subscribers

When the YouTuber uploads a new video:

- All subscribers get a notification
- The YouTuber does not manually message each subscriber
- Subscribers can subscribe or unsubscribe anytime

The YouTuber (subject) does not know who the subscribers are — they just notify everyone on the list.

Another analogy: **Newsletter subscription**.

- You subscribe to a blog
- When a new post is published, you get an email
- The blog does not know you personally — it just sends to all subscribers

## TypeScript Example

### Step 1: Define the Observer Interface

```ts
interface Observer {
  update(data: any): void;
}
```

### Step 2: Create the Subject

```ts
class Stock {
  private observers: Observer[] = [];
  private price: number = 0;

  // Add an observer
  attach(observer: Observer): void {
    this.observers.push(observer);
  }

  // Remove an observer
  detach(observer: Observer): void {
    const index = this.observers.indexOf(observer);
    if (index > -1) {
      this.observers.splice(index, 1);
    }
  }

  // Notify all observers
  private notify(): void {
    for (const observer of this.observers) {
      observer.update(this.price);
    }
  }

  // Change state and notify
  setPrice(newPrice: number): void {
    this.price = newPrice;
    this.notify();
  }

  getPrice(): number {
    return this.price;
  }
}
```

### Step 3: Create Concrete Observers

```ts
class PriceDisplay implements Observer {
  update(price: number): void {
    console.log(`Price Display: Stock price is now $${price}`);
  }
}

class ChartDisplay implements Observer {
  update(price: number): void {
    console.log(`Chart Display: Adding $${price} to chart`);
  }
}

class AlertSystem implements Observer {
  private threshold = 150;

  update(price: number): void {
    if (price > this.threshold) {
      console.log(`Alert: Price exceeded $${this.threshold}!`);
    }
  }
}
```

### Step 4: Use the Pattern

```ts
const stock = new Stock();

// Create observers
const priceDisplay = new PriceDisplay();
const chartDisplay = new ChartDisplay();
const alertSystem = new AlertSystem();

// Observers subscribe
stock.attach(priceDisplay);
stock.attach(chartDisplay);
stock.attach(alertSystem);

// Update price — all observers are notified automatically
stock.setPrice(100);
// Price Display: Stock price is now $100
// Chart Display: Adding $100 to chart

stock.setPrice(160);
// Price Display: Stock price is now $160
// Chart Display: Adding $160 to chart
// Alert: Price exceeded $150!

// Unsubscribe an observer
stock.detach(chartDisplay);

stock.setPrice(200);
// Price Display: Stock price is now $200
// Alert: Price exceeded $150!
// (Chart Display does not get notified)
```

**What happened:**

- Observers subscribe to the stock.
- When the stock price changes, all observers are automatically notified.
- The stock does not know what the observers do — it just calls `update()`.

## JavaScript Version (Event Emitter Style)

JavaScript has built-in support for this pattern via `EventEmitter` (Node.js) or custom events (browser).

```js
class Stock {
  constructor() {
    this.observers = [];
    this.price = 0;
  }

  subscribe(observer) {
    this.observers.push(observer);
  }

  unsubscribe(observer) {
    this.observers = this.observers.filter(obs => obs !== observer);
  }

  notify() {
    this.observers.forEach(observer => observer(this.price));
  }

  setPrice(newPrice) {
    this.price = newPrice;
    this.notify();
  }
}

// Usage with functions as observers
const stock = new Stock();

const priceLogger = (price) => console.log(`Price: $${price}`);
const alertChecker = (price) => {
  if (price > 150) console.log("Alert: High price!");
};

stock.subscribe(priceLogger);
stock.subscribe(alertChecker);

stock.setPrice(100); // Price: $100
stock.setPrice(160); // Price: $160 \n Alert: High price!
```

## Real-World Examples

### 1. React State Management

React's state system is Observer pattern:

```jsx
function App() {
  const [count, setCount] = useState(0);
  
  // When count changes, React notifies all components using it
  return (
    <div>
      <h1>Count: {count}</h1> {/* Observer 1 */}
      <p>Double: {count * 2}</p> {/* Observer 2 */}
      <button onClick={() => setCount(count + 1)}>Increment</button>
    </div>
  );
}
```

---

### 2. DOM Event Listeners

```js
const button = document.getElementById("myButton");

// Multiple observers subscribe to the same event
button.addEventListener("click", () => console.log("Observer 1: Button clicked"));
button.addEventListener("click", () => console.log("Observer 2: Logging click"));
button.addEventListener("click", () => console.log("Observer 3: Sending analytics"));

// Clicking the button notifies all observers
```

---

### 3. Node.js EventEmitter

```js
const EventEmitter = require("events");

class UserService extends EventEmitter {
  createUser(name) {
    console.log(`Creating user: ${name}`);
    this.emit("userCreated", { name });
  }
}

const userService = new UserService();

// Observers
userService.on("userCreated", (user) => {
  console.log(`Sending welcome email to ${user.name}`);
});

userService.on("userCreated", (user) => {
  console.log(`Adding ${user.name} to analytics`);
});

userService.createUser("Alice");
// Creating user: Alice
// Sending welcome email to Alice
// Adding Alice to analytics
```

## How the Pattern Solves the Problem

| Before (Manual Notification) | After (Observer) |
|---|---|
| Subject knows about all observers | Subject knows nothing about observers |
| Adding observers means editing subject | Observers subscribe dynamically |
| Tight coupling | Loose coupling |
| Hard to extend | Easy to extend |

---

## Advantages

✅ **Loose coupling** — subject and observers are independent  
✅ **Open/Closed Principle** — add observers without modifying subject  
✅ **Dynamic subscriptions** — observers can subscribe/unsubscribe at runtime  
✅ **Broadcast communication** — one change notifies many  
✅ **Reusability** — observers can be reused with different subjects

---

## Disadvantages

⚠️ **Memory leaks** — forgetting to unsubscribe can cause memory leaks  
⚠️ **Unpredictable order** — observers are notified in subscription order, which may not be obvious  
⚠️ **Performance** — notifying many observers can be slow  
⚠️ **Difficult debugging** — hard to trace who is observing what

---

## When Should I Use It?

Use Observer when:

✅ One object's change should trigger updates in multiple others  
✅ You want loose coupling between objects  
✅ You need dynamic subscriptions (subscribe/unsubscribe at runtime)  
✅ You are building event-driven systems  

**Common use cases:**

- **Event systems** (click handlers, keyboard events)
- **State management** (React, Vue, Redux)
- **Real-time updates** (stock prices, chat messages)
- **Logging/analytics** (track events across the app)
- **Notifications** (email, SMS, push)

---

## When Should I NOT Use It?

Avoid Observer when:

❌ Only one object needs to react  
❌ The relationship is simple and direct  
❌ The order of notifications matters strictly

## Common Mistakes

### Mistake 1: Forgetting to Unsubscribe

```js
class Component {
  constructor(stock) {
    stock.subscribe((price) => {
      this.render(price);
    });
  }
}

// When component is destroyed, the observer still exists
// Memory leak!
```

**Fix:** Always unsubscribe when the observer is destroyed.

```js
class Component {
  constructor(stock) {
    this.stock = stock;
    this.observer = (price) => this.render(price);
    stock.subscribe(this.observer);
  }

  destroy() {
    this.stock.unsubscribe(this.observer);
  }
}
```

---

### Mistake 2: Modifying Subject Inside Observer

```js
class BadObserver implements Observer {
  update(price: number) {
    // ❌ Modifying the subject inside the observer
    stock.setPrice(price + 10); // Infinite loop!
  }
}
```

**Rule:** Observers should **react**, not **modify** the subject.

## Observer vs Pub/Sub (Common Confusion)

| | Observer | Pub/Sub |
|---|---|---|
| **Coupling** | Subject knows observers exist (maintains list) | Publisher and subscriber never know each other |
| **Mediator** | No middleman | Event bus / message broker in the middle |
| **Relationship** | Direct (one-to-many) | Indirect (via event bus) |
| **Use case** | Tight components in same app | Loosely coupled systems (microservices) |

**Example of Pub/Sub:**

```js
// Event bus (mediator)
class EventBus {
  constructor() {
    this.events = {};
  }

  subscribe(event, callback) {
    if (!this.events[event]) this.events[event] = [];
    this.events[event].push(callback);
  }

  publish(event, data) {
    if (this.events[event]) {
      this.events[event].forEach(callback => callback(data));
    }
  }
}

const eventBus = new EventBus();

// Publisher does not know about subscribers
eventBus.publish("userCreated", { name: "Alice" });

// Subscriber does not know about publisher
eventBus.subscribe("userCreated", (data) => {
  console.log(`User created: ${data.name}`);
});
```

## Related SOLID Principles

### Open/Closed Principle (OCP)

✅ You can add new observers without modifying the subject.

### Single Responsibility Principle (SRP)

✅ The subject's responsibility is managing its state. Observers' responsibility is reacting to changes.

---

## Related Design Patterns

### Mediator

Both decouple objects. Mediator centralizes communication through a mediator object. Observer broadcasts directly to observers.

### Pub/Sub

Pub/Sub is Observer with a middleman (event bus). The publisher and subscribers never know each other.

## Interview Questions

**Q1: What is the Observer pattern?**  
A: A pattern where a subject maintains a list of observers and notifies them automatically when its state changes.

**Q2: What is the difference between Observer and Pub/Sub?**  
A: Observer has direct coupling (subject knows observers). Pub/Sub uses an event bus — publisher and subscriber never know each other.

**Q3: How does this work in JavaScript?**  
A: DOM event listeners, React state, and Node.js EventEmitter all use Observer.

**Q4: What are the disadvantages?**  
A: Memory leaks if you forget to unsubscribe, unpredictable notification order, and performance issues with many observers.

**Q5: When would you use it?**  
A: When one object's change should trigger updates in multiple others, and you want loose coupling.
